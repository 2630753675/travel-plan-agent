# MVP 后续优化计划

范围：只做已确认的 6 项 —— **2 追问失败提示、4 统计与版本一致性、5 旧代码清理、7 追问质量、8 追问进度持久化、12 可观测性**。

不包含：结构化追问字段（1）、追问耗时体验（6）、移动端追问核对（9）、地图 API（10）、真实库存（11）。这些留到后续，不夹带。

原则：

- 每个阶段一个可验收结果、一个提交；
- 每个阶段同步更新文档，文档与代码同一个提交；
- 阶段完成后在会话里报告：改了什么、怎么验证、提交号；
- 不改变 MVP 已确认的产品方向。

## 阶段 1：追问失败可见、可重试（第 2 项）

**状态**：已完成（2026-11-20），提交 `fix: 追问生成失败可见并可重试`。

**问题**

`preparePlan` 捕获所有异常后直接 `runPlan()`，模型失败、超时、接口 500 都表现为“没有追问”，用户无法判断。

**改动**

后端 `POST /api/plan/questions`：

- 返回 `{questions, warning, retryable}`；
- 区分可重试（超时、429、5xx）与不可重试（未配置模型、参数错误）；
- warning 只返回安全文案，不含密钥、请求头。

前端：

- 新增 `questionState: 'idle' | 'loading' | 'error'` 与 `questionError`；
- 失败时不自动开跑，需求页显示提示条：
  - “追问生成失败：超时。”
  - `重试`：重新调用；
  - `直接开始`：调用 `runPlan()`；
- 成功且 0 条问题仍直接开跑；
- 提示条不遮挡表单，移动端换行。

**测试**

- 接口 mock 500 / timeout / 正常空列表；
- 前端：失败后不跳运行页；点重试重新请求；点直接开始进入运行。

**文档**

- `docs/mvp-status.md` 更新限制第 3 条；
- README 或 API 文档补 `/api/plan/questions` 的失败语义。

**提交**

`fix: 追问生成失败可见并可重试`

**验收**

模拟失败时用户能选择“重试/直接开始”，不再静默降级。

## 阶段 2：统计与版本口径统一（第 4 项）

**状态**：已完成（2026-11-20），提交 `fix: 方案统计与版本口径统一`。

**问题**

- `/api/plan/{id}` 只有方案记录，不含 `llm_stats`；刷新后分享页/方案页丢调用数；
- 计划 `version` 与团队 `approved_version` 编号不同，界面同时出现两个 vN，用户分不清。

**改动**

统计：

- 完成运行时把 `llm_stats` 写入 plan 记录（或 `get_plan` 联查最近一次 completed run）；
- `GET /api/plan/{id}` 返回 `llm_stats`；
- 旧记录没有 stats 时返回空对象，不报错。

版本：

- 明确一个用户可见版本号：方案版本 `version`；
- 团队批准版本只作为内部质量字段，映射到方案版本后展示；
- 方案页、分享页、版本列表统一使用同一字段；
- 文档写清两个版本号的含义，避免再次混用。

**测试**

- 完成一次运行后 `GET /api/plan/{id}` 含 `llm_stats`；
- 刷新页面后调用数不丢；
- 方案页与分享页版本号一致；
- 旧记录兼容。

**文档**

- `docs/mvp-status.md` 更新限制第 4、5 条；
- README 补版本口径说明。

**提交**

`fix: 方案统计与版本口径统一`

**验收**

同一方案在运行页、方案页、分享页看到的调用数与版本号一致。

## 阶段 4：追问质量约束与评测（第 7 项）

**状态**：已完成（2026-11-20），提交 `feat: 追问质量约束与评测样本`。

**问题**

同一需求两次调用返回的问题不同，可能问泛问题、重复问题，或问“答案不改变行程”的问题。

**改动**

提示词：

- 默认最多 2 条，只有确实必要才 3 条；
- 每条问题必须说明“答案如何改变行程”，写不出就不问；
- 禁止询问已明确字段；
- 禁止重复：标题与选项语义重复的合并。

后端：

- 去重：标题归一化后相似度过高则丢弃；
- 上限从 3 降为 2（可配置）；
- 对 `kind=ask` 且没有可执行选项的问题直接丢弃；
- 记录 `dropped_reasons` 到日志，便于评估。

评测：

- 新增 `backend/scripts/eval_followups.py`；
- 10 条固定需求样本（家庭/老人/预算紧/日期近/无偏好/远途等）；
- 指标：是否 0 问、是否重复、是否泛问、是否与字段冲突；
- 输出 JSON 报告到 `docs/eval-followups.json`；
- 模型调用有成本，脚本手动运行，不放进 CI。

**测试**

- mock 模型返回重复问题 → 只保留 1 条；
- 返回 3 条 → 截断为 2 条；
- 返回空 → 0 条直接开跑。

**文档**

- `docs/mvp-status.md` 更新限制第 1、7 条；
- 评测报告随提交入库。

**提交**

`feat: 追问质量约束与评测样本`

**验收**

评测报告中重复/泛问为 0；最多 2 条；空结果路径正常。

## 阶段 5：追问进度刷新可恢复（第 8 项）

**状态**：已完成（2026-11-20），提交 `feat: 追问进度刷新可恢复`。

**问题**

在追问页刷新会丢问题、答案和当前卡，用户要重新生成（再花一次模型调用）。

**改动**

- 用 `sessionStorage` 保存草稿：
  - `form`、`briefText`、`followups`、`followAnswers`、`followDrafts`、`followIndex`；
  - key 带 schema 版本，避免旧结构污染；
- 页面加载时恢复，仅在 `screen === 'followup'` 且数据完整时生效；
- 开始规划、返回入口、新建行程时清空；
- 恢复后校验问题 id/索引，不合法则丢弃重来。

**测试**

- 追问页刷新 → 问题、答案、当前卡恢复；
- 开始规划后刷新 → 不恢复旧追问；
- 新建行程 → 清空。

**文档**

- `docs/mvp-status.md` 更新限制第 7 条。

**提交**

`feat: 追问进度刷新可恢复`

**验收**

## 阶段 6：运行指标与可观测性（第 12 项）

**状态**：已完成（2026-11-20），提交 `feat: 运行指标与可观测性`。

**问题**

每次运行的模型调用、token、耗时、返工轮次、失败原因只存在于 SSE 日志，无法按运行对比，也无法排查“为什么这次慢/贵”。

**改动**

后端：

- 复用 `runs` 表已有字段，补 `duration_ms`、`rounds`、`turns`、`stop_reason`；
- 新增 `GET /api/metrics/runs?limit=20`（访问口令保护）：
  - plan_id、created_at、calls、tokens、latency、passed、rounds、failure_type；
- 失败运行也落一条记录，区分 `llm_error / budget / protocol / timeout / cancelled`；
- 日志加 `plan_id` 关联，不记录密钥和完整提示词。

前端：

- 设置面板加“运行指标”入口（内部用，不放进主流程）；
- 表格：时间、调用数、tokens、耗时、轮次、结果；
- 单行展开显示失败原因。

**测试**

- 完成一次运行后指标接口有记录；
- 失败运行有记录且原因正确；
- 未授权访问返回 401。

**文档**

- 新增 `docs/observability.md`：字段含义、接口、排障流程；
- `docs/mvp-status.md` 更新限制第 8 条。

**提交**

`feat: 运行指标与可观测性`

**验收**

能在页面上看到最近运行的调用数、tokens、耗时和失败原因。

## 顺序与理由

1. **1 失败提示**：先让用户不被静默降级；
2. **2 统计/版本**：先让数据可信；
3. **3 清理旧图**：降低后续改动误判；
4. **4 追问质量**：在可信基础上提升内容；
5. **5 持久化**：减少重复模型调用；
6. **6 可观测性**：让后续优化有数据；
7. **7 回归与文档**：收口。

预计工作量：阶段 1–2 各 0.5–1 天，阶段 3 半天，阶段 4–6 各 1 天，阶段 7 半天。
