## 高危（建议优先修）

### H1 决策工具与其它工具同批返回时，历史损坏
- 位置：`backend/app/agents/runtime.py:455-502`（`submit_decision` 分支提前 `return`）。
- 现象：模型一次响应里若先给 `submit_decision`、再给普通工具调用，代码只回填决策的 `tool` 消息就返回，其它调用留下“未闭合的 assistant.tool_calls”。
- 复现：`.harness/audit_probe.py` 的 P3 → `HISTORY CORRUPT: assistant tool_calls 未闭合`。
- 影响：下一回合触发 `history_repaired` 静默丢弃上下文；严重时表现为“回合失败/方案重做”。
- 建议：返回前为其余调用补合成 `tool` 结果（`{"ok": false, "error": "本回合未执行：已提交决策"}`），或强制决策必须是响应中的最后一个调用。

### H2 工具重放只比较 id/agent/tool，不比较参数
- 位置：`runtime.py:503-512`。
- 现象：`ctx.operations` 以模型给的 `tool_call_id` 为键；同一 Agent 复用了 id（部分供应商/自建模型会生成 `call_1` 这类可重复 id）且参数不同，会直接返回**旧结果**。
- 复现：`.harness/audit_probe2.py` 的 P4 → `replayed old result instead of running new args: True`。
- 影响：读到过期事实；写工具的重放会跳过真实副作用却报告成功。
- 建议：operations 键改成 `(agent, tool, call_id, arguments_hash)`，或重放前比较 `arguments`。

### H3 单日重排/回滚会让“团队交付视图”失效
- 位置：`backend/app/api/main.py:493-506`（`get_plan` 用 `row.itinerary == record.itinerary` 匹配交付）、`664-707`（refine 用旧流水线覆盖）、`730-761`（rollback）。
- 复现：`.harness/audit_probe3.py` → 重排前 `document/ledger/approved_version` 有值，重排后三者全为 `None`。
- 影响：
  - 团队方案的「计划书 / 问题清单 / 批准版本」在重排或回滚后消失（前端刷新即丢）；
  - refine 用单 Agent 流水线重建交通住宿，绕过了团队评审与固定事件、`approved_version`，方案不再与团队会话对应；
  - 前端 rollback 还把旧的 `document/team_tasks/issue_ledger` 留在内存（`frontend/src/App.tsx:1219-1224`），页面显示“旧计划书 + 新行程”。
- 建议：团队方案禁止直接 refine/rollback，改为“发起新一轮团队返工”；或把交付视图做成独立表并以 `plan_version` 关联，不再靠 itinerary 相等匹配。

### H4 返工工具限制只写不清，传播型返工继承旧限制
- 位置：`hub.py:950-961` 写入 `task["allowed_repair_tools"]`；`826-828` 据此限制工具；全仓库 **2 处赋值、0 处清理**。
- 场景：T2 先因“送机重复”被返工（工具限于 `replace/remove_fixed_event` + 只读/落定工具），交付后因“预算超支”（责任方 logistics、`propagate=True`）再次变成 pending。此时 local_expert 没有 scoped issue，**旧的工具限制仍在**，`assign_pois` 等写工具被禁，任务可能改不动而耗尽回合。
- 证据：`.harness/audit_probe.py` 的 P2 源码扫描。
- 建议：任务重新进入 pending 时清除该字段；仅在“本次确有 scoped issue”的派工上与 runtime 共享。
