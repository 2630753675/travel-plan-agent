# Peer 多 Agent 整改计划

> 2026-11-17 单模式改造：`fast` / `expert` 已删除，系统只保留深度团队。本文是历史整改记录，保留用于追溯；其中提到的 fast/expert/legacy 分支已不再适用。

## 目标与边界

本轮聚焦显式深度模式 `peer`。目标是把它做成可诊断、可恢复、事实可追溯的分层多 Agent 编排：专业判断由 Agent 通过消息协作完成；代码负责确定性调度、工具权限、版本状态、硬约束、安全预算和持久化。当前实现属于集中式调度，不声称 Agent 自主唤醒或并行。

不调用真实模型/API 验收。使用 mock、脚本化模型和临时检查点验证。保留现有用户媒体、截图、运行数据及其他未提交改动。

## 已确认基线

- 实测运行 `d81356d8e404`：34.4 秒、5 次供应商请求、3 个 Agent 回合；Orchestrator 的首轮约 16.1 秒；Logistics 空响应后整场退出。
- peer 升级事件已产生，但 `peer_ask` 中断未写入 checkpoint；当前工作区 `_run_graph` 成功路径未获取 snapshot，之后访问 `snapshot.values/tasks` 会崩溃。
- `max_model_calls=8`、`max_agent_turns=10` 与当前角色协议所需调用数不匹配；工具调用也计入供应商请求预算。
- peer 硬约束未通过时到达复审上限会直接 `END`；预算 blocker 使既有 confirm 路由不可达；Writer 的硬校验会阻止接受风险后的交付。
- `_persist` 同步全量序列化共享快照；真实检查点约 70.2 MB/405 个线程；固定 `.tmp` 路径存在并发竞争风险。
- `wake` 字段经过验证但不参与调度；会话按 `next_agent` 串行运行，这是本轮明确的架构语义，不实现自由抢占或并行。
- 现有 `verify_peer_agents.py` 使用废弃角色协议，需迁移后才能作为 peer 回归依据。

## 分阶段修改计划

### 阶段 1：运行可观测与中断可靠性（P0）

- 成功完成图流后先获取状态快照，再检查 `tasks.interrupts`；snapshot 读取失败要转为有明确错误的运行事件，不得空异常。
- 为 API 捕获异常增加结构化日志和 `runs` 载荷：异常类型、消息、阶段/Agent、run id、traceback（服务日志），注意不记录 API key/完整授权头。
- `chat_tools` 保留并报告 finish_reason、reasoning_content/空响应等诊断；只对明确瞬时错误做有限重试，重试有上限且计入实际请求数。
- 将确定性运行状态与可恢复中断分离；服务异常不得误标可恢复，真实 interrupt 必须可持久化。

验收：mock 图进入 `peer_ask` 后 API 返回 `run_interrupted`，checkpoint 有 interrupt；故意抛出异常时持久化非空异常类型与消息、服务日志含 traceback；空响应和超时按有限次数重试后升级/失败，不静默中断。

### 阶段 2：Agent 调度协议与交付语义（P1）

- 明确命名为集中式调度器：Agent 的 `wake` 是协作意图/事件元数据；代码依据任务依赖、责任方和消息来排下一位 Agent。避免文档声称 peer-to-peer scheduler。
- 调整 peer 调用预算与角色协议一致；明确 `max_model_calls` 是真实供应商请求总数，Agent 回合是独立概念。运行上限默认值必须有 mock 成功路径依据，达到硬上限时如实升级，不谎称“模型失败”或“已完成”。
- 修复 `_validate_tasks` 错误信息，将未知 owner、重复 ID、缺失 goal、未知依赖、循环依赖分别指出；Critic 作为评审角色不得被错误地要求成为专业交付任务。
- 硬约束未通过时 Critic 给出责任方和基于工具结果的 changes；budget/时间/人群问题可返工，达到上限后向用户呈现具体 issue 及选项。当前版本禁用 `accept_risk`，任何确定性 blocker 都不能被用户选择绕过或伪称通过。
- 修正升级原因分类：模型瞬时失败、调用/时间上限、任务不可执行、用户取舍、事实不足分别给出真实原因和可执行下一步。

验收：脚本化五角色模型在设定预算内成功完成；单项工具/Agent 瞬时失败后能有限重试或准确升级；预算 blocker 可到用户确认；上限升级文案与实际计数一致。

### 阶段 3：事实与内容可靠性（P1）

- evidence 必须引用本轮工具调用结果 ID/结构化事实键；校验器验证引用存在且属于当前会话，空泛的非空字典不算证据。
- 失败工具结果、缺失字段、估算数据与已核实事实需区分；模型不得把“候选”写成“预订”或把坐标直线距离写成道路时间。
- Writer 输出逐日摘要和 practical_notes 要能映射到获批行程与已知事实；拒绝无来源的价格、时间、服务承诺和预订状态。不能可靠校验的自由文本使用受限模板/事实字段生成。

验收：伪造 evidence 引用被拒绝；有效工具引用通过；Writer 编造事实的脚本化输出被拒绝；待确认字段被保留且不补造。

### 阶段 4：检查点与数据增长（P2）

- 已完成按 thread_id 分片：旧 `checkpoints.pkl` 只读兼容，新写入落到 `checkpoints.pkl.d/*.pkl`，单次写入只序列化当前线程；异步写入在工作线程完成并原子替换，实例级锁串行化，删除线程写 tombstone 分片。
- 设计明确保留策略前不删除既有运行数据；分片体积/写入时间观测与清理策略仍是后续工作。
- 把 Agent 回合边界变为可恢复边界前先明确如何持久化工具上下文、消息总线、历史和预算计数，避免重复计费/重复副作用。

验收：并发 checkpoint 写入无临时文件冲突；服务事件循环不被全量序列化阻塞；旧 checkpoint 可读取；迁移/清理不丢活动中断。

### 阶段 5：回归、文档与运行验收

- 已新增 `verify_peer_success.py`：脚本化五角色完整成功路径（24 次调用、6 个 Agent 回合、总价 5700/8000）与评审上限后的用户升级；`verify_peer_remediation.py` 覆盖中断恢复、停止终态、空响应/超时、事实引用与 checkpoint 并发。
- 后端编译、前端构建、事件协议、差异检查通过；不调用真实模型/API。
- 文档区分已验证事实、未验证假设及真实模型需由用户执行的验收项。
